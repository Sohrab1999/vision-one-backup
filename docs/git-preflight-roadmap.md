## ۲) SOP پیش‌بررسی — الزامات اجباری هر گام اجرایی آینده

> قالب هر گام (مطابق قرارداد اسناد مخزن): هدف · عملیات مجاز · عملیات ممنوع · معیار تأیید · شرایط توقف.
> همهٔ فرمان‌های وضعیت با `--no-optional-locks` اجرا شوند. اجرای هر گام تنها با مجوز صریح کاربر.

### P-0 — خط مبنا (اجباری، ابتدای هر گام)
- **هدف:** انجماد وضعیت قابل راستی‌آزمایی پیش از هر تغییر.
- **عملیات مجاز:** `git rev-parse HEAD`، `branch --show-current`، `status --short --branch`، `ls-remote backup refs/heads/main`، `log -1`؛ ثبت در گزارش گام.
- **ممنوع:** هر عملیات نوشتن؛ فرض «مخزن همان دفعهٔ قبل است».
- **معیار:** branch = `main`؛ HEAD + status + SHA ریموت ثبت و مقایسه شده؛ اگر HEAD جلوتر از آخرین گزارش شناخته‌شده است، commit(های) واسط با `git log`/`git show --name-status` شناسایی و **auto-commit پلتفرمی از کارِ جاری تفکیک** شود.
- **توقف:** واگرایی `main ≠ backup/main`؛ درخت کثیفِ بدون توضیح؛ وضعیت مبهم.

### P-1 — تعریف `ALLOWED_FILES` (پیش از هر ویرایش)
- **هدف:** محدودهٔ دقیق و صریح فایل‌های گام جاری.
- **قواعد:** فهرست مسیرهای مشخص repo-relative (بدون wildcard)؛ هر فایل خارج فهرست = خارج از گام؛ گام اجرایی = یک قدم roadmap؛ فهرست در گزارش گام قبل از اولین ویرایش اعلام شود.

### P-2 — طبقه‌بندی تغییرات موجود (pre-existing vs task-owned)
- **هدف:** هیچ تغییر از-پیش‌موجود یا فایل پلتفرمی به کارِ جاری نسبت داده نشود.
- **قواعد:** اقلام `status --short` در P-0 با برچسب «pre-existing» ثبت شوند؛ فایل‌های پلتفرمی (`tool-results/`، PID، …) همیشه «خارج از گام»؛ حفظ کامل آن‌ها؛ هیچ پاک‌سازی/untrack/حذفی.
- **توقف:** هم‌پوشانی pre-existing با `ALLOWED_FILES` یا منشأ نامعلوم → S3.

### P-3 — گیت توقف پیش از staging
- **هدف:** اطمینان از روشنی کامل وضعیت پیش از هر `git add`.
- **معیار:** P-0/P-1/P-2 کامل و بدون مورد مبهم؛ در غیر این صورت فقط گزارش + توقف.

### P-4 — استیجینگ محدود
- **قواعد:** فقط `git add <مسیرهای مصرح ALLOWED_FILES>`؛ فاصلهٔ stage تا commit حداقل (پنجرهٔ رقابت با auto-commit پلتفرمی)؛ **ممنوع مطلق:** `git add -A`، `git add .`، `git add -u`، `git commit -a`، `--no-verify`، `--amend`.
- **توقف:** وجود فایل staged ناخواسته → فقط گزارش؛ unstage (`restore --staged`/`reset`) = عملیات تغییردهنده و نیازمند مجوز صریح.

### P-5 — راستی‌آزمایی stage (تنها سد پیش از push خودکار)
- **عملیات مجاز:** `git diff --cached --name-status` (باید **دقیقاً برابر** `ALLOWED_FILES` باشد — تطبیق مجموعه‌ای)؛ بازبینی کامل `git diff --cached` (اسکن secret/PII/db/محتوای حساس)؛ `git diff --check` و `git diff --cached --check`.
- **معیار:** فهرست staged == allowlist (نه بیشتر، نه کمتر)؛ صفر نشانهٔ whitespace/حل‌تعارض؛ صفر مورد حساس؛ اگر گام شامل تغییر کد است: `bun run lint` و بررسی تایپ نسبت به خط مبنای P-0 (بدون خطای جدید).
- **توقف:** هر مغایرت فهرست، هر مشبههٔ حساس، هر خطای کیفیت جدید → S4.

### P-6 — کیفیت پیش از commit
- **هدف:** هیچ commitی بدون راستی‌آزمایی کیفیت متناسب با دامنهٔ گام.
- **قواعد:** حداقل `bun run lint`؛ اگر دامنه شامل تایپ/داده است، `tsc`/راستی‌آزمایی داده؛ نتایج در شواهد گام ثبت شود؛ مقایسه فقط نسبت به خطاهای پایهٔ شناخته‌شدهٔ P-0.

### P-7 — commit و راستی‌آزمایی ریموت
- **قواعد:** `git commit -m "<پیام مصرح، متصل به شناسه گام>"`؛ سپس ثبت `git rev-parse HEAD`؛ هوک خودکار push می‌کند (**اجرای دستی هوک ممنوع**)؛ پس از ≥ ۲۰ ثانیه: `git ls-remote backup refs/heads/main` باید **دقیقاً** SHA محلی باشد؛ دُم `/tmp/devhook.log` (فقط خواندن) برای `auto-push OK/FAILED`.
- **ممنوع (هرگز به‌عنوان بازیابی خودکار):** force-push / `--force-with-lease`، reset/rebase/rewrite history، حذف فایل، تغییر remote/هوک/config.
- **توقف/ثبت شکست:** `auto-push FAILED` یا مغایرت SHA پس از ۶۰ ثانیه = **شکست صریح** (نه موفقیت ضمنی) → گزارش + توقف؛ اگر بین stage و commit یک auto-commit پلتفرمی فرود آمد، فقط وضعیت دوباره راستی‌آزمایی شود؛ هرگز rebase نشود.

### P-8 — ثبت شواهد و به‌روزرسانی مستندات
- **قواعد:** شواهد هر گام: SHA قبل/بعد، فهرست فایل‌ها، آزمون‌ها، وضعیت ریموت، خطوط لاگ هوک — در گزارش گام (گفتگو)؛ credential هرگز آشکار نشود؛ به‌روزرسانی `roadmap.md`/`worklog.md` **فقط در محدودهٔ مصرح همان گام** و با مجوز؛ ادعای موفقیت بدون تطبیق SHA ریموت ممنوع (BLOCKED به‌جای موفقیت).

## ۳) قواعد سراسری (در همهٔ P-0…P-8)

- ممنوع مطلق: `git add -A` / `git add .` / `git add -u` / `git commit -a` / `--no-verify` / `--amend` / force-push / `git reset` / `git clean` / `git stash` / `git checkout -- <path>` / `git gc` / `git prune` / تغییر `core.hooksPath`.
- فرمان‌های وضعیت با `--no-optional-locks`؛ `git fetch` = تغییردهنده (رف‌های remote-tracking) → فقط با مجوز صریح.
- مسیرهای حساس (بخش ۰) هرگز stage/commit/حذف/untrack نشوند؛ محتوای آن‌ها خوانده نشود (فقط نام مسیر/وضعیت گیت/متادیتا).
- هیچ credential/token/URL دارای اعتبار بدون پالایش چاپ یا نمایش نشود.
- commit/push خودکار پلتفرمی مستقل از گام جاری است؛ فرض نشود مخزن محلی بی‌تغییر مانده — P-0 در ابتدا و P-7 در انتها همیشه تازه اجرا شود.
- هر commit/push غیرمنتظره حین گام: با SHA گزارش و پیش از ادامه بررسی شود.
- history و دیتابیس‌ها مقدس‌اند: هیچ بازنویسی/حذفی به‌عنوان بازیابی خودکار.
- رویهٔ بازگشت عمومی: برای commit مستندات فقط `git revert <sha>` (بدون بازنویسی تاریخ)؛ برای هر تغییر دیگر، بازگشت فقط با مجوز صریح و با ثبت شواهد قبل/بعد.

| # | وضعیت | واکنش |

| S1 | تغییر pre-existing خارج از محدوده | گزارش؛ هیچ تمیزکاری |
| S2 | فایل staged ناخواسته | گزارش؛ unstage فقط با مجوز صریح |
