## ۱. اصول طراحی (چهار تصمیم بنیادی)

| # | تصمیم | rationale |
|---|---|---|
| D1 | **دو مرجع حقیقت، با مرز شفاف:** سرویس = مرجع «سؤال/داوری/ساعت»؛ میزبان = مرجع «تخته» (تاس، حرکت، جهش، برد) | roadmap صریح است: «منبع حقیقت تاس = میزبان». داوری سؤال سمت سرویس می‌ماند تا تضمین G4 («پاسخ هرگز زودتر از reveal به کلاینت نمی‌رسد») حفظ شود — مرورگر میزبان به‌هرحال به کتاب دسترسی دارد، مرورگر مهمان نه |
| D2 | **اتاق‌های واریانت‌دار:** مدل اتاق G4 دست‌نخورده می‌ماند و فقط فیلد `variant: 'quiz' \| 'sl'` می‌گیرد؛ join اتاق با واریانت دیگر رد می‌شود | صفر ریسک رگرسیون برای دوئل quiz زندهٔ G4؛ زیرساخت (کد ۴رقمی، گرس rejoin، TTL، cleanup، سقف ۳۰۰ اتاق) دوباره مصرف می‌شود |
| D3 | **بدون پیش‌بینی سمت مهمان:** مهمان هرگز حرکت را خودش محاسبه نمی‌کند؛ فقط ردِ رویدادهای دریافتی را با مدت‌های ثابت همان بازی انیمیت می‌کند (STEP_MS=۱۲۰، JUMP_MS=۵۲۰، ۵ فلیپ × ۹۰ms) | حذف کامل کلاس باگ «دو تختهٔ ناهمگام»؛ تأخیر شبکه فقط روی «لحظهٔ شروع» انیمیشن اثر دارد نه روی درستی مسیر |
| D4 | **ساعت نوبت = سرویس، نه هیچ کلاینتی** | تایمر توقف‌پذیرِ محلی (`Q_TIME_MS=۲۰۰۰۰` + زنجیرهٔ بی‌توقف) طراحی تک‌کاربره است؛ دوئل به ساعت بی‌طرف نیاز دارد — `TURN_MS = ۲۵٬۰۰۰ms` (۵ ثانیه بیشتر از محلی، برای جذاب RTT) |

## ۲. مدل اتاق (افزودنی‌های مجاز به `Room` در سرویس)

```
variant: 'sl'                          // توسط create ست می‌شود
config: { rules:{exact,capture,timed}, boardSeed:string }   // فقط میزبان تعیین می‌کند
sl: {
  seq: number                          // شمارندهٔ مونوتونیک هر تغییر وضعیت — گارد پیام‌های کهنه
  positions: [number, number]          // خانهٔ ۱..۱۰۰ هر بازیکن (۱ = خانهٔ شروع، مطابق بازی محلی)
  turn: number                         // اندیس بازیکن فعال (0=میزبان، 1=مهمان)
  lastState: object | null             // آخرین sl_state میزبان — سلاحِ rejoin
  rollSeq: number                      // تشخیص تکراری sl_roll
}
```

سقف‌های موجود دست‌نخورده: `MAX_PLAYERS=۲`، `MAX_PACK=۳۰`، گرس `۶۰s`، TTL لابی `۳۰min`/تمام‌شده `۱۵min`، پالایش `sanitizePack`/`sanitizeName` همان.

## ۳. پروتکل پیام‌ها

### ۳-۱. رویدادهای موجود G4 که عیناً مصرف می‌شوند (بدون تغییر امضا)

`create` (با فیلد افزودنی `variant:'sl'`) → `created` · `join` → `joined` · `rejoin` · `start` · `disconnect` · `error`

### ۳-۲. رویدادهای نوِ فضای‌نام `sl_`

| جهت | رویداد | بار (فیلدهای کلیدی) | صادرکننده |
|---|---|---|---|
| C→S | `sl_answer` | `{ qIndex, choice, seq }` | بازیکن فعال (هر دو جهت ممکن) |
| C→S | `sl_roll` | `{ rollId, value(۱..۶), by }` | **فقط میزبان** |
| C→S | `sl_move` | `{ rollId, from, to, trace:{ steps:number[], jumps:[{kind:'snake'\|'ladder', from, to}], extra(تاس۶), captured? } , seq }` | **فقط میزبان** |
| C→S | `sl_finish` | `{ winner: 0\|1, reports }` | **فقط میزبان** (دیده‌شدن خانهٔ ۱۰۰) |
| C→S | `sl_state` | اسنپ‌شات کامل §۲-`sl` + `config` | **فقط میزبان** — بعد از هر حرکت کامل؛ سرویس فقط ذخیره و فوروارد می‌کند |
| S→C | `sl_question` | `{ qIndex, text, options(بدون پاسخ), endsAt, serverNow, turn, seq }` | سرویس — به **هر دو** بازیکن (جعبهٔ سؤال مشترک؛ تماشاگر هم سؤال را می‌بیند) |
| S→C | `sl_answered` | `{ qIndex, choice, correct, answer, by }` | سرویس بلافاصله بعد از داوری (فردیِ پاسخ‌دهنده؛ در مار و پله هر نوبت یک پاسخ‌دهنده است → reveal فوری) |
| S→C | `sl_roll` / `sl_move` | عین بار فرستنده | سرویس — فوروارد به حریف (+ تأیید به میزبان) |
| S→C | `sl_turn_expired` | `{ qIndex, turn, seq }` | سرویس — ساعت مستقل؛ دیررس‌های `sl_answer` بعدش رد می‌شوند |
| S→C | `sl_state` | عین بار میزبان + `serverNow` | سرویس — فوروارد + پاسخ rejoin |
| S→C | `sl_finished` | `{ winner, reason:'win'\|'host_left'\|'guest_left', reports }` | سرویس |

گاردهای سرویس روی هر رویداد `sl_`: واریانت اتاق، بازیکنِ فعال، `seq` مونوتونیک، یک‌بارمصرف‌بودن `rollId`، شکل پیام (بدون تفسیر منطق تخته). rate-limit همان الگوی G4.

### ۳-۳. توالی یک نوبت کامل

```
سرویس: sl_question → هر دو
بازیکن فعال: sl_answer → سرویس (داوری با pack دارای answer)
سرویس: sl_answered (شامل answer برای reveal) → هر دو
میزبان: انیمیشن تاس محلی (۵×۹۰ms) → sl_roll → سرویس → هر دو
میزبان: walk/jump با مدت‌های ثابت → sl_move (رد کامل مسیر) → سرویس → هر دو
میزبان: sl_state (چک‌پوینت، ذخیره در sl.lastState) → سرویس → هر دو
  ├─ value=۶ یا قانون گرفتار/پله → تکرار توالی با سؤال بعدی (نوبت اضافه = همان بازیکن)
  └─ پایان: قهرمان = خانهٔ ۱۰۰ → sl_finish → سرویس → sl_finished
```

قوانین opt-in (فرود دقیق/گرفتار) کاملاً سمت میزبان اعمال می‌شوند و در `trace` منعکس می‌شوند — سرویس از منطق تخته بی‌خبر می‌ماند (D1).

## ۴. قطعی و دوباره‌اتصال

| سناریو | رفتار |
|---|---|
| مهمان قطع ≤۶۰s | گرس G4؛ برگشت با `rejoin` → سرویس `sl_state` (از `sl.lastState`) + اگر سؤال باز است `sl_question` دوباره با همان `endsAt` |
| مهمان قطع >۶۰s | `sl_finished {reason:'guest_left', winner:میزبان}` — پیروزی با گذر |
| **میزبان قطع >۶۰s** | **پایان منفق (DoD SL4-01):** سرویس `sl_finished {reason:'host_left'}` با برنده = موقعیت مقدم؛ برابری خانه‌ها = مساوی. هر دو کلاینت Attempt خودشان را ذخیره می‌کنند |
| قطع حین انیمیشن | v1 جبران نمی‌کند (فنس F4) — چک‌پوینت بعدی `sl_state` وضعیت را صادق می‌کند |

## ۵. جعبهٔ سؤال و اتمام pack

pack میزبان با `sanitizePack` G4 (سقف ۳۰) سرو می‌شود؛ ترتیب = شافل سرویس در `start` (سکه‌اندازی شروع‌کننده هم سرویس، بی‌طرف). pack طولانی مار و پله (۵۸ پاسخ در QA ثبت‌شده) ممکن است تمام شود → **چرخه با شافل دوباره** و ثبت `cycle` در reports (تکرار سؤال پذیرفته‌شده و آشکار). SRS/مدرس فقط برای پاسخ‌های «خودِ بازیکن» در مرورگر خودش ثبت می‌شود (خطای حریف به SRS من آلوده نمی‌شود).

## ۶. UX کلاینت (افزودنی‌های `snakes-ladders-game.tsx`)

1. **حالت سوم setup** «آنلاین با دوست» کنار «هم‌صفحه»/«ربات» — فقط پس از گو (SL4-01).
2. **افست مهره‌ها:** دو مهره در یک خانه → جابجایی افقی ±۱۲٪ عرض خانه بر اساس اندیس بازیکن با `TOKEN_BG` موجود (این رفع بصری در همهٔ حالت‌ها هم اعمال می‌شود — افزودنی کوچک مجاز همان فایل).
3. تایمر نوبت = نوار `sl-q-timer` موجود، اما `endsAt/serverNow` از `sl_question` (D4). توقف‌پذیری زنجیرهٔ بی‌توقف در آنلاین بی‌معناست و آن مسیر کد فعال نمی‌شود.
4. **کلید `visionone:sl-save:<bookId>` در حالت آنلاین هرگز نوشته نمی‌شود** (تعارض با rejoin سرویس) — flush آن مسیر با گارد `mode==='online'` می‌پرد.
5. Attempt: `category:'duel-sl'` + `detail.boardSeed/rules` موجود + نام حریف.

## ۸. تصمیم گو/ناگو (DoD این کار)

**تصمیم: ✅ گو مشروط** — اجرای SL4-01 مجاز است، منوط به رعایت هم‌زمان:

1. فنس‌های F1..F6 این سند بلااستثنا رعایت شوند؛
2. اجرای فازبندی‌شده با کامیت جدا در هر زیرگام:
   **SL4-01a** سرویس (فضای‌نام `sl_*` + واریانت + ساعت نوبت) → **SL4-01b** کلاینت میزبان (roll/move/state) → **SL4-01c** کلاینت مهمان + rejoin → **SL4-01d** QA دو کلاینت واقعی از گیت‌وی ۸۱ + قطعی + Attempt + موبایل ۳۹۰؛
3. پیش‌شرط زیرساخت قبل از هر سشن QA: `free -m` (درس OOM سندباکس)، تک‌اینستانس dev، reload بعد از ادیت (درس باندل کهنه)؛
4. پلن بازگشت: یک کامیت برای کل فاز → `git revert` فقط همان، SL0..SL3 بی‌اثر.
