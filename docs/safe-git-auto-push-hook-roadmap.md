## A. شرح مسئله (Problem Statement)

هوک `post-commit` (مسیر `.git/hooks/post-commit`) پس از **هر** commit محلی دو کار انجام می‌دهد:

1. **خطوط ۱۳–۲۴:** نگه‌داری سرور توسعه — اگر پورت 3000 سرو نشده باشد `bun run dev` را راه می‌اندازد (در چهار چرخهٔ اخیر همیشه `port 3000 already served, skip`).
2. **خطوط ۲۶–۳۵:** زیرشل جداشده‌ای که ۲ ثانیه صبر می‌کند و در **خط ۳۰** اجرا می‌کند:

   ```bash
   if git push --force backup main >> "$LOG" 2>&1; then
   ```

توکن `--force` یعنی اگر `main` محلی و `backup/main` ریموت واگرا شده باشند، push **تاریخچهٔ ریموت را بازنویسی می‌کند** و هر commit «فقط-ریموت» یتیم می‌شود (بر اساس یافته‌های جلسات پیشین، همین سازوکار در از‌دست‌رفتن زنجیرهٔ SR-3 با commitهای `a2d6ffd`/`cc4b496` نقش داشت). حذف `--force` رفتار عادی بک‌آپ را **حفظ می‌کند** (وقتی local جلوتر است، push همان fast-forward همیشگی است) و فقط در حالت واگرایی، push را به‌جای بازنویسیِ بی‌صدا، **با شکست آشکار** متوقف می‌کند.

### A.۱ چهار بازیگر مستقل (بر پایهٔ شواهد — نباید با هم خلط شوند)

1. **commitهای خودکار پلتفرم:** ران‌تایم کانتینر وقتی درخت کار «کثیف» است مستقلاً commit می‌سازد (کادنس مشاهده‌شده ≈ ۳۵±۳ دقیقه): committer همیشه `Z User <z@container>` و پیام commit رشتهٔ UUID است. چهار نمونه در 2026-10-20: `fc10e8b` (12:03)، `e701ae3` (12:40)، `bd55198` (13:15)، `444bfcd` (14:14) — همگی UTC. هوک **هیچ** commitی نمی‌سازد و فقط پس از commitِ عامل دیگری اجرا می‌شود. **اصلاح یا حتی حذف هوک، این commitها را متوقف نمی‌کند.**
2. **هوک post-commit مخزن:** اسکریپت محلی داخل `.git/hooks/` که توسط گیت ردیابی نمی‌شود (در `git status`/`git diff` دیده نمی‌شود و در تاریخچهٔ مخزن نسخه‌برداری نمی‌شود). کامنت خط ۴ خودش را این‌گونه معرفی می‌کند: `Fired by the platform runtime's auto-commits (persistent process tree).`
3. **push خودکار به GitHub:** توسط خط ۳۰ هوک، ۳–۵ ثانیه پس از هر commit. چهار نمونه در `/tmp/devhook.log`: `9b15de3..fc10e8b`، `fc10e8b..e701ae3`، `e701ae3..bd55198`، `bd55198..444bfcd` — هر چهار fast-forward با نتیجهٔ `auto-push OK`. توکن `--force` است که در صورت واگرایی، بازنویسی تاریخ را **ممکن** می‌سازد؛ تا امروز هر چهار چرخه fast-forward بوده‌اند.
4. **ماندگاری Workspace مستقل از GitHub:** ران‌تایم پلتفرم وضعیت workspace (فایل‌ها، `db/custom.db`، `upload/`) را مستقل از نتیجهٔ push نگه می‌دارد؛ ثبت‌شدن `auto-push FAILED` در لاگ تاکنون هرگز مانع ادامهٔ کار پلتفرم نشده است. **بک‌آپ GitHub و ماندگاری workspace دو سازوکار جدایند؛ این نقشه راه فقط رفتار push بک‌آپ را تغییر می‌دهد.**

نکتهٔ مکمل: «بک‌آپ خودکار گیت‌هاب (push بعد از هر commit)» در سند `نقشه راه ها/نقشه-راه-جامع-توسعه-۲۰۲۶.md` (خط ۷) به‌عنوان زیرساخت **عمدی** ثبت شده است. پس هدف این نقشه راه، حذف بک‌آپ خودکار **نیست**؛ فقط حذف رفتار بازنویسی‌کنندهٔ `--force` است.

### A.۲ سه واقعیت ساختاری که برنامه را محدود می‌کنند

- **هوک untracked است:** چون داخل `.git/` قرار دارد، هرگز stage/commit نمی‌شود و گیت تغییرش را گزارش نمی‌کند. تنها ابزار نمایش تفاوت، diff مستقیم فایل (`diff -u` با کپی پشتیبان در `/tmp`) یا `git diff --no-index` است. نتیجه: در گام ۴، commit فقط **مستندات** تغییر را ثبت می‌کند؛ خودِ تغییر هوک با بازرسی مستقیم فایل (گام‌های ۲–۳) راستی‌آزمایی می‌شود، نه با تاریخچهٔ گیت.
- **ویرایش بلافاصله فعال می‌شود:** حالتِ «آماده ولی غیرفعال» وجود ندارد؛ بلافاصله پس از گام ۱، نخستین commit بعدی — به احتمال زیاد یک auto-commit پلتفرم تا ~۳۵ دقیقه بعد — **بدون** `--force` push می‌شود. بنابراین گام ۱ عملاً «نقطهٔ فعال‌سازی» است. پیش‌شرط گام ۱ (عدم واگرایی) تضمین می‌کند نخستین pushِ تحت‌تأثیر از نظر رفتاری با وضع فعلی یکسان باشد.
- **ریسک باز — provisioning پلتفرم:** کانتینر به‌طور دوره‌ای بازسازی می‌شود (بر اساس یافته‌های جلسات پیشین: پاک‌شدن `/tmp` با ماندن refs؛ ری‌استارت همهٔ پروسه‌ها حول 11:45 UTC). نامعلوم است که آیا پلتفرم هنگام بازسازی، هوک را از قالب خودش بازتأمین می‌کند و ویرایش را بی‌صدا برمی‌گرداند یا نه. این مجهول عمداً به‌عنوان **ریسک حل‌نشده** (بخش D) ثبت شده و پیش از هر اتکا به محتوای هوک و پس از هر بازسازی باید دوباره راستی‌آزمایی شود.

## C. برنامهٔ اجرایی چک‌لیستی (Checkbox Execution Plan)

**قواعد اجرا:** هر گام = یک اقدام مستقل + یک گزارش + **توقف برای دریافت مجوز گام بعدی**. هیچ گامی با گام دیگری ترکیب نمی‌شود.

### گام ۰ — خط مبنا و پیش‌بررسی ایمنی (فقط-خواندنی)

- [ ] گام ۰ اجرا شد
1. **هدف:** انجماد خط مبنای قابل راستی‌آزمایی (HEAD، refs، وضعیت درخت، محتوای دقیق هوک) تا هر گام بعدی نسبت به آن سنجیده شود و واگرایی پیش از هر ویرایش کشف گردد.
2. **محدوده:** فقط پرس‌وجوهای فقط-خواندنی گیت و خواندن `.git/hooks/post-commit` و `/tmp/devhook.log`. هیچ چیزی تغییر نمی‌کند.
3. **عملیات مجاز:** `git rev-parse HEAD main backup/main`، `git status --short`، `git log --oneline -10`، `git reflog -10`، `git show --stat <sha>`، `sha256sum .git/hooks/post-commit`، `stat -c '%a' .git/hooks/post-commit`، خواندن فایل‌ها.
4. **عملیات ممنوع:** هر عملیات نوشتن گیت (add/commit/push/fetch/…)، هر دسترسی شبکه، هر ویرایش فایل، build/test، مدیریت پروسه.
5. **معیار تأیید:** (الف) `main` و `backup/main` یک SHA چاپ کنند؛ (ب) `git status --short` خالی باشد؛ (ج) خط ۳۰ هوک عیناً `if git push --force backup main >> "$LOG" 2>&1; then` باشد؛ (د) sha256 هوک و مجوز 755 ثبت شده باشد.
6. **شواهد قابل جمع‌آوری:** خروجی دستورات + sha256 + مهر زمانی، در گزارش گام (در گفتگو) ثبت شود؛ داخل مخزن هیچ فایلی ساخته نشود.
7. **رویهٔ بازگشت:** لازم نیست (هیچ تغییری ایجاد نشده).
8. **شرایط توقف:** `main ≠ backup/main` (واگرایی → ادامه ممنوع تا بررسی)؛ درخت کثیفِ بدون توضیح؛ خط ۳۰ بدون `--force` باشد (یعنی تغییر قبلاً توسط عامل دیگری انجام شده → فقط گزارش، بدون ویرایش)؛ وقوع auto-commit جدید حین پیش‌بررسی → گرفتن خط مبنای تازه و گزارش آن.

### گام ۱ — آماده‌سازی (و فعال‌سازی) تغییر حداقلی هوک

- [ ] گام ۱ اجرا شد
1. **هدف:** حذف فقط توکن `--force` از خط ۳۰؛ بقیهٔ فایل بایت‌به‌بایت دست‌نخورده؛ تضمین بازگشت‌پذیری کامل.
2. **محدوده:** فقط `.git/hooks/post-commit` خط ۳۰، به‌همراه یک نسخهٔ پشتیبان **خارج از مخزن**: `/tmp/post-commit.baseline-<date>.sh` (عمداً خارج از مخزن، تا درخت کار کثیف نشود و auto-commit اضافه تولید نکند).
3. **عملیات مجاز:** `cp .git/hooks/post-commit /tmp/post-commit.baseline-<date>.sh`؛ `sha256sum` قبل/بعد؛ ویرایش در‌جا فقط خط ۳۰: `git push --force backup main` → `git push backup main`؛ راستی‌آزمایی مجوز 755 پس از ویرایش.
4. **عملیات ممنوع:** ویرایش هر خط یا هوک دیگر؛ تغییر `core.hooksPath`؛ commit؛ push؛ اجرای دستی هوک؛ دست‌زدن به نگه‌بان dev server (خطوط ۱۳–۲۴) یا مسیرهای لاگ.
5. **معیار تأیید:** `diff -u /tmp/post-commit.baseline-<date>.sh .git/hooks/post-commit` فقط یک hunk در خط ۳۰ نشان دهد که دقیقاً `--force ` را حذف کرده؛ مجوز فایل همچنان 755؛ تعداد خطوط فایل تغییر نکرده باشد.
6. **شواهد قابل جمع‌آوری:** خروجی diff؛ sha256 قبل/بعد؛ خروجی `stat -c '%a'`.
7. **رویهٔ بازگشت:** `cp /tmp/post-commit.baseline-<date>.sh .git/hooks/post-commit` سپس تطبیق sha256 با مقدار مبدنا و مجوز 755.
8. **شرایط توقف:** امکان ساخت نسخهٔ پشتیبان نباشد؛ diff بیش از یک تغییر نشان دهد؛ مجوز فایل ≠ 755. **اذعان صریح در متن مجوز:** این گام «نقطهٔ فعال‌سازی» است — نخستین commit پس از آن (احتمالاً auto-commit پلتفرم تا ~۳۵ دقیقه بعد) بدون `--force` push می‌شود؛ اگر تا آن لحظه واگرایی رخ داده باشد push **شکست می‌خورد** (این دقیقاً رفتار مطلوب جدید است) و در `/tmp/devhook.log` به‌صورت `auto-push FAILED` ثبت می‌شود.

### گام ۲ — راستی‌آزمایی syntax و بازرسی دقیق diff بدون تحریک هوک

- [ ] گام ۲ اجرا شد
1. **هدف:** اثبات اعتبار نحوی اسکریپت ویرایش‌شده و یگانه‌بودن تغییر در یک توکن.
2. **محدوده:** فقط فایل هوک و نسخهٔ مبنای `/tmp`.
3. **عملیات مجاز:** `bash -n .git/hooks/post-commit` (فقط بررسی نحوی — اسکریپت را اجرا **نمی‌کند**)؛ `diff -u`؛ `git diff --no-index /tmp/post-commit.baseline-<date>.sh .git/hooks/post-commit`؛ خواندن فایل با شماره خط.
4. **عملیات ممنوع:** اجرای هوک یا هر بخشی از آن؛ ساخت commit آزمایشی (هر commitی هوک را شلیک می‌کند)؛ `git commit --allow-empty`؛ stage کردن هر چیزی.
5. **معیار تأیید:** `bash -n` بدون خروجی و با کد خروج ۰؛ diff دقیقاً یک hunk شامل `-  if git push --force backup main …` و `+  if git push backup main …`؛ هیچ hunk دومی نباشد؛ بخش نگه‌بان (خطوط ۱۳–۲۴) و مسیر لاگ دست‌نخورده باشند.
6. **شواهد قابل جمع‌آوری:** نتیجهٔ `bash -n`؛ diff کامل؛ گزیدهٔ خط‌شماره‌دار خطوط ۲۶–۳۵.
7. **رویهٔ بازگشت:** همان رویهٔ بازگشت گام ۱.
8. **شرایط توقف:** هر خطای syntax؛ ظهور هر hunk اضافه؛ تغییر بخش نگه‌بان.

### گام ۳ — تأیید محدودبودن تغییر و مستندسازی بازگشت

- [ ] گام ۳ اجرا شد
1. **هدف:** ممیزی نهایی پیش از commit — اثبات اینکه هیچ چیز دیگری در مخزن یا پیکربندی تغییر نکرده و رویهٔ بازگشت آماده و خواناست.
2. **محدوده:** وضعیت کل درخت کار؛ فایل هوک؛ همین سند (فقط برای تیک‌زدن چک‌باکس‌ها).
3. **عملیات مجاز:** `git status --short`؛ `git rev-parse HEAD main backup/main`؛ هش مجدد هوک و کپی مبدنا؛ خواندن هوک؛ به‌روزرسانی چک‌باکس‌های همین سند.
4. **عملیات ممنوع:** هر ویرایش دیگرِ هوک؛ ویرایش سایر فایل‌ها؛ commit؛ شبکه؛ تغییر پروسه‌ها.
5. **معیار تأیید:** `git status --short` هیچ ورودی غیرمنتظره‌ای نداشته باشد (تغییر هوک برای گیت نامرئی است و جداگانه با sha256 راستی‌آزمایی می‌شود)؛ sha256 هوک برابر مقدار پس از گام ۱ باشد؛ تنها تفاوت کپی مبدنا با هوک فعلی خط ۳۰ باشد؛ دستورات بازگشت عیناً در گزارش نقل شوند.
6. **شواهد قابل جمع‌آوری:** خروجی status؛ دو مقدار sha256؛ مهر زمانی.
7. **رویهٔ بازگشت:** بازگشت گام ۱ (بازیابی از `/tmp` + تطبیق هش و مجوز).
8. **شرایط توقف:** هر ورودی غیرمنتظره در درخت؛ عدم تطبیق هش با نتیجهٔ گام ۱؛ واگرایی جدید `backup/main` نسبت به `main` → پیش از گام ۴ توقف و گزارش.

### گام ۴ — commit و push گام انجام‌شده (فقط پس از مجوز صریح برای اجرا و انتشار)

- [ ] گام ۴ اجرا شد
1. **هدف:** ثبت و انتشار محصول کارِ تأییدشده. **نکتهٔ دامنه (پرچم انحراف از صورت‌مسئله):** خود فایل هوک به‌دلیل قرارگیری داخل `.git/` ذاتاً قابل commit نیست؛ بنابراین commit فقط **مستندات مصرح** (این نقشه راه و worklogِ مصوب جداگانه) را ثبت می‌کند و تغییر هوک با بازرسی مستقیم فایل (گام‌های ۲–۳) راستی‌آزمایی می‌شود. اگر نسخه‌برداری گیت از خود هوک مطلوب باشد، به سازوکار جداگانه‌ای نیاز دارد (مثل دایرکتوری hooks ردیابی‌شده + اسکریپت نصب) که **خارج از محدودهٔ این نقشه راه** است و باید جداگانه طرح شود.
2. **محدوده:** فقط مسیرهای از‌پیش‌مصوب (حداقل: `docs/safe-git-auto-push-hook-roadmap.md`؛ worklog فقط در صورت مصوبهٔ جداگانه). هیچ چیز دیگری.
3. **عملیات مجاز:** `git add <مسیرهای مصرح>`؛ `git status` و `git diff --cached --stat` برای بازرسی stage؛ `git commit -m "<پیام مصوب>"`؛ پس از commit، خواندن دُم `/tmp/devhook.log` و `git rev-parse HEAD`.
4. **عملیات ممنوع:** stage کردن هر فایل دیگر (runtime، `tool-results/`، `db/`، `upload/`)؛ `--no-verify`؛ `--amend`؛ هر فلگ force؛ reset/rebase؛ push دستی (push را هوک انجام می‌دهد)؛ هر درخواست شبکه‌ای غیر از push خودِ هوک (و راستی‌آزمایی ریموت در صورت مجوز صریح).
5. **معیار تأیید:** `git show --stat HEAD` فقط مسیرهای مصرح را فهرست کند؛ SHA جدید ثبت شود؛ `/tmp/devhook.log` پس از commit نشان دهد `post-commit fired` و سپس `auto-push OK` (یا در صورت واگرایی `auto-push FAILED` → **توقف و گزارش؛ به‌هیچ‌وجه force نشود**)؛ تأیید اینکه ریموت دقیقاً همان SHA را دارد، از طریق `git ls-remote backup refs/heads/main` **فقط در صورت مجوز صریح شبکه** یا از طریق بررسی کاربر در رابط GitHub.
6. **شواهد قابل جمع‌آوری:** SHA؛ خروجی `git show --stat`؛ خطوط لاگ هوک با مهر زمانی؛ SHA ریموت (اگر کانال تأیید موجود باشد).
7. **رویهٔ بازگشت:** برای commit مستندات: `git revert <sha>` (commit جدید — بدون بازنویسی تاریخ؛ هرگز reset نشود). برای هوک: رویهٔ بازگشت گام ۱.
8. **شرایط توقف:** فایل غیرمصرح در stage؛ فرود یک auto-commit پلتفرم بین stage و commit (فقط وضعیت دوباره راستی‌آزمایی شود؛ هرگز rebase نشود)؛ لاگ هوک pushِ ردشده (واگرایی) را نشان دهد → توقف، گزارش، انتظار برای دستور.

## D. الزامات ایمنی (Safety Requirements)

- [ ] هرگز از `--no-verify` استفاده نشود (این کار دقیقاً هوکِ تحت‌تعمیر را دور می‌زند).
- [ ] هرگز هوک‌های گیت به‌صورت سراسری غیرفعال نشوند (حذف هوک، خالی‌کردن محتوای آن، تغییر `core.hooksPath`).
- [ ] هرگز `git push --force`، `git push --force-with-lease` یا هر دستور بازنویسی‌کنندهٔ تاریخ اجرا نشود.
- [ ] هرگز `git reset`، `git clean`، `git checkout`، `git switch`، `git gc` یا `git prune` اجرا نشود.
- [ ] هرگز بک‌آپ یا سند roadmap موجود بازنویسی نشود؛ ایجاد دایرکتوری جدید `roadmaps/` بدون مجوز انجام نشود.
- [ ] `.gitignore`، فایل‌های runtime (`db/custom.db`، `upload/`، `tool-results/`، فایل‌های PID)، محتوای دیتابیس، آپلودها و سایر فایل‌های اپلیکیشن تغییر نکنند.
- [ ] build، test یا عملیات دیتابیس انجام نشود.
- [ ] در فاز برنامه‌ریزی هیچ دسترسی شبکه‌ای انجام نشود؛ در اجرای آینده، شبکه فقط برای push خودِ هوک و راستی‌آزمایی ریموتِ مصرح.
- [ ] هرگز credential، token، cookie یا URL ریموت بدون پالایش چاپ یا نمایش داده نشود.
- [ ] هرگز موفقیت push بدون راستی‌آزمایی SHA دقیق روی ریموت ادعا نشود؛ اگر راستی‌آزمایی ممکن نبود، **BLOCKED** گزارش شود نه موفقیت.
- [ ] پیش از هر پیاده‌سازی، ناسازگاری احتمالی workspace/branch و رفتار auto-commit پلتفرم بررسی شود؛ فرض نشود تغییرات محلی همیشه به‌صورت ایمن مانده‌اند.
- [ ] **ریسک حل‌نشده:** ممکن است provisioning پلتفرم، هوک را بازنویسی/برگرداند (به‌ویژه پس از بازسازی کانتینر). پیش از هر اتکا به محتوای هوک و پس از هر بازسازی، با `sha256sum` و خواندن خط ۳۰ دوباره راستی‌آزمایی شود.
- [ ] هر commit یا push خودکارِ غیرمنتظره در طول اجرا باید با SHA گزارش و پیش از ادامه بررسی شود.

## E. سیاست commit و انتشار (برای پیاده‌سازی آیندهٔ مصرح)

- بلافاصله پیش از commit: HEAD فعلی، درخت کار، برنچ هدف (`main`) و وضعیت ریموت (`backup/main` از رف‌های محلی) راستی‌آزمایی شود.
- هیچ فایل بی‌ربطی stage نشود؛ فایل‌های runtime نباید در commit جمع شوند.
- پیش از commit، تغییرات stage‌شده بازرسی شود (`git diff --cached --stat` به‌همراه diff کامل).
- فقط تغییر هوکِ مصرح (به‌صورت مستندات مصرح — خودِ هوک ذاتاً untracked است، بنگرید گام ۴) و مستندات مصرح نقشه راه/worklog کامیت شوند.
- SHA دقیق commit ثبت شود و انطباق دامنه با `git show --stat HEAD` تأیید شود.
- تأیید شود ریموت دقیقاً همان SHA را دارد (`git ls-remote backup refs/heads/main` در صورت مجوز صریح، یا تأیید کاربر در رابط GitHub).
- اگر ریموت واگرا شده بود: **توقف.** برای موفق‌سازی push هیچ force-push، reset، rebase یا بازنویسی تاریخی انجام نشود.
- هر commit یا push خودکارِ غیرمنتظره پیش از ادامه بررسی شود (SHA، فایل‌ها، committer، لاگ هوک).
- اگر راستی‌آزمایی commit یا push ممکن نبود، به‌جای ادعای موفقیت **BLOCKED** گزارش شود.

## F. معیارهای پذیرش این سند (Acceptance Criteria)

- [x] هوک فعلی و تغییر رفتاری تک‌خطیِ مقصود (خط ۳۰ — حذف `--force`) را دقیق شناسایی می‌کند.
- [x] برنامه‌ریزی را از اجرا جدا می‌کند (هیچ گامی اجرا نشده؛ هر گام با مجوز جداگانه گیت شده است).
- [x] پیش از هر گام اجرایی، مجوز جداگانه را صریحاً الزامی می‌کند.
- [x] بازگشت (rollback) و رسیدگی به شکست را برای هر گام لحاظ کرده است.
- [x] حفظ تمام commitها و داده‌های بی‌ربط را تضمین می‌کند (بدون بازنویسی، پاک‌سازی یا untrack).
- [x] هیچ ادعای بدون‌پشتوانه‌ای دربارهٔ کنترل‌های پلتفرم ندارد (هر گزارهٔ مربوط به پلتفرم به شواهد مشاهده‌شده متصل است و مجهولات صریحاً «حل‌نشده» علامت خورده‌اند).
- [x] از قرارداد مستندسازی نقشه راه موجود مخزن پیروی می‌کند (محل `docs/`، الگوی نام `<topic>-roadmap.md`، جدول شناسنامهٔ خط مبنای تاریخ‌دار، چک‌لیست اجرایی).
